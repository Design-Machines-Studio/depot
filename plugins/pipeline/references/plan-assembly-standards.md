# Assembly production architecture standards (plan adversary)

Loaded by `plan-adversary` Perspective 3 only when the target project is
Assembly / Baseplate (Go + Templ + Datastar with `internal/fixtures/`). A plan
for any other project never loads this file and is judged on the general stack
conventions and guardrails in the agent definition.

When the plan targets Assembly (`assembly-baseplate` or `internal/fixtures/`), verify:

- **Current trust model:** review trusted first-party Fixture code for the current two-developer/private-repository context unless approved scope actually introduced an untrusted author or public marketplace boundary. Do not model trusted Fixture authors as hostile third parties. Apply isolation controls only to a named reachable boundary or current data-integrity failure.
- **Mutation applicability:** each mutation criterion follows `assembly:development`'s Mutation Applicability Matrix and names its obligation -- present behavior, approved requirement, current consumer/contract, or realistic consequence. Protected user/operator writes require concrete action/resource authorization before write; trusted maintenance needs an explicit trust boundary. Do not demand an event, audit entry, transaction, SSE broadcast, service layer, or extra acceptance criterion without naming why it applies here.
- **Event completeness:** where a current consumer, cross-module contract, real-time projection, or existing event contract creates an obligation, the event publishes AFTER commit; never infer the obligation from SQLite mutation syntax alone.
- **Execution-scope economy:** criteria prove a requirement or realistic failure mode, not merely lengthen scope; drop criteria serving only bulk or size parity.
- **ScopedDB enforcement:** block a raw `*sql.DB` path only when it permits a current cross-prefix read/write, authorization bypass, or corruptible state that `ScopedDB` is the existing mechanism for preventing; name that path and harm. Mere raw-DB use by trusted first-party code is not automatically a P1.
- **Fixture SDK conformance (Baseplate PR #440):** when approved scope changes an SDK boundary or a reachable input can violate an existing invariant, require the smallest negative test proving that invariant; a zero-value authorizer or actor allowing a protected user/operator action is a blocker. Do not require a full conformance harness, marketplace defenses, or unrelated negative-test families merely because trusted first-party code lives under `internal/fixtures/`.
- **Membership and settings data integrity (Baseplate PR #447):** membership, settings, or permissions rows require server-issued stable row identity (never array index or DOM order), cloned rows regenerating their ID, fail-closed validation on unknown or missing fields, and a live-region announcement for every async row mutation.
- **Size and layering heuristics:** file/function length, layer count, interfaces, and service/repository patterns matter only when they reveal a concrete execution failure or approved-scope regression; numeric thresholds and architecture preferences are signals, never blockers. A clear, tested, one-use handler or concrete implementation is valid.
- **Federation security:** federation endpoints (if any) are HTTPS-only with validated `return_url`; link tokens need 5-minute TTL, single-use nonce, audience validation.
- **Federation reactivity (Baseplate PR #271/#275, #273/#277):** cross-install push/share/notification requires signed push payloads verified against the pinned key BEFORE processing (idempotent, replay-protected); SSE fan-out re-authorizing each subscriber per emit and scoping events to the granted resource; and a real two-install verification (live sender + receiver) as the acceptance bar, not a single-install mock.
- **Behavior-preserving decomposition:** decompositions of oversized trust/share/repair/membership/federation files (e.g. #234, #258) are move-only: target files + line counts, named stable public symbols, existing test suite as proof, no new behavior or tests. Flag logic edits mixed with the move, changed exported signatures, or whole-struct DTOs across the new seam.
- **Release / updater supply chain (Baseplate PR #279):** require verify-before-extract (checksum + signature against a pinned key before extraction or exec), extraction safety (zip-slip/symlink/size guards), snapshot-before-apply with recoverable partial-success and atomic handoff, GoReleaser dry-run only in CI (no real publish/sign), and provider-agnostic manifest origins. A 'verified' claim with no actual verify call is a BLOCKER.
- **Production readiness preflight (Baseplate PRs #399, #438, #436/#437):** config loading, updater, release tooling, shutdown, and key rotation work require: config validation **fail-closed at boot** (invalid config exits non-zero, never defaults through); an **update candidate preflighted before replacement** (checksum + signature + version ordering verified before any file is swapped -- #438); update-failure recovery copy naming the recovery command; explicit shutdown ordering (drain HTTP -> stop consumers -> flush -> close DB, not an incidental `defer` stack); email and federation key rotation with responder-side key-check fairness and a stated old-key grace window; server-side double-submit protection on repair/recovery forms (idempotency token, not a disabled button); and a **release receipt** enumerating active-install monitoring and beta-finalization proof (#436/#437). Update runbooks and docs in the same scope; flag validation that warns and continues.
- **Federation share transport, both sides (Baseplate PR #447):** cover the **responder**: serving shared assets (install logo, document preview), checking the requesting key fairly, and re-checking the share grant on every fetch, not once at link time. Enforce the **public/private URL boundary**: never serialize an internal base URL (`http://app:8080/...`, LAN hostname, `localhost:port`) into a federated payload; derive cross-install asset URLs from configuration, not the inbound `Host` header; refuse to emit a payload when the public URL is unset rather than fall back to the internal address; validate that a signed inbound fetch targets a resource covered by the grant (a signature proves *identity*, never *authorization*). Flag a single-install mock acceptance bar.
- **Input validation:** external input is validated before every write; when the applicability matrix selects a service boundary, the validated DTO crosses it, not raw request data.
- **Migration sequencing:** sequential migration numbers, no gaps or duplicates; every schema migration precedes the handler/service work depending on it. Verify with `ls migrations/*.sql | sort | tail -1` in the target repo.
- **Destructive confirmation:** delete/archive/revoke require server-verified confirmation (confirmation token or re-authentication); client-only `confirm()` is insufficient.
- **Generated Templ files:** `*_templ.go` never appears in acceptance criteria or `filesToModify` -- only `.templ` sources. Flag any reference as a BLOCKER.
- **Install / auth-boundary browser proof (Baseplate PR #278, #274):** prove reachable allowed/denied/stale-direct-request states and server-side validation of async-populated defaults at the affected interface. An existing Auth Boundary Map may help; do not require a new threat-model document or receipt solely for review.
- **[Full only] Companion skills validation:** Assembly-targeting chunks include `assembly:development` in `companionSkills`; missing companion skills cause subagents to miss domain conventions.
