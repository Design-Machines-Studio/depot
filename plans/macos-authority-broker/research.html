Research: independent authority for external-provider dispatch

Executive conclusion

The existing OpenRouter path has a sound ordered-byte snapshot mechanism but no independent authority: the repository worker selects the mode, can calculate the supplied approval digest, inherits the API key, performs the request, and writes an unsigned receipt. The strongest practical repair for the accepted small-team boundary is broker-owned provider transport.

Selected: extend the root-owned Go broker with a separate provider-dispatch subsystem. Within a FIDO-approved closed run, one indivisible broker transaction receives bounded exact bytes, applies installed policy, consumes a single-use operation authorization, rehashes, sends to a pinned origin with a broker-only key, bounds the response, and emits a signed result/cleanup chain.

Do not confuse three meanings of “provider”: the local authority provider, imported repository-verification evidence, and outbound model transport are separate contracts. Existing provider_attestation remains inbound verification evidence and cannot authorize disclosure.

Trust boundaries and same-UID guarantee

      ▼

      └── provider family ───── scanner ── pinned TLS origin ── OpenRouter
                    ▲                 │
same-UID worker ────┘ untrusted request bytes/metadata only
                    └── no key, no bearer grant, no signed-result minting

Candidate containers are launched without network and without broker, Docker, FIDO, credential, state, or service-manager mounts. A same-UID host repository worker may still have ordinary internet access on a developer workstation. Without a separate OS principal and host egress policy, the product cannot honestly prevent all TCP calls made with the worker's own credentials. The supported authoritative guarantee is narrower and useful: the worker cannot read or use the broker's production key, cannot ask the broker to leave the approved scope, and cannot forge the broker-signed result chain. A strict “only broker can reach OpenRouter” deployment remains an optional, separately proven host-firewall lane and is not a parity/release claim until both OSes pass it.

Closed dispatch protocol

The public request is dispatch_provider_request. Authorization and transmission are one broker transaction. Internally it creates three signed artifact roles—provider_request_authorization, provider_result, and provider_cleanup—but never returns a reusable capability. cancel_provider_request can cancel only the exact active request under the same run/session. provider_transport_status is read-only and content-free. authorize_external_disclosure and record_provider_result are internal transitions, not caller-controlled success operations.

The daemon atomically reserves nonce/sequence and cumulative run budget before scanning or transport. Failure before network contact records a denied/declined result without a send. Once transport begins, the sequence remains consumed even on cancellation, timeout, partial response, or restart recovery.

Exact request and policy binding

The authorization digest covers a closed canonical object containing:

  • ordered system/user part manifest; for every part: role, ordinal, byte count, SHA-256, media type, and sanitized logical label;
  • combined length-delimited manifest digest; aggregate payload byte count and approved maximum;
  • canonical origin exactly https://openrouter.ai/api/v1, operation path, redirect-disabled transport identity, and production/test credential class;
  • requested model, ordered optional fallback models, workload class, provider-routing policy digest, disclosure-security policy digest, scanner build/version/digest, response byte/token/time bounds;
  • repository descriptor/scope, run and authorization event, profile, trusted base, candidate commit and snapshot, include-worktree flag, cadence boundary, lane, authority digest, and substrate digest when the dispatched work depends on contained evidence;
  • nonce, strict sequence, boot ID, session ID, issued/expiry, single-use flag, prior-chain digest, and cumulative run-call/payload/response budget.

Unknown fields, missing fields, reordering, downgrade, null-vs-value changes, altered bytes, or mismatched live state fail closed.

Payload, credential, and transport custody

  • The client sends length-prefixed binary-safe frames; it does not use shell command substitution or pass content/path/key through argv or environment. UTF-8 text is required for OpenRouter content; malformed UTF-8 and binary parts are rejected before network contact.
  • Default bounds are frozen by installed policy: 1 MiB per IPC frame, 256 parts, 8 MiB aggregate request, 8 MiB aggregate response, 16-level JSON depth, and explicit token/time ceilings. Smaller run-specific limits may be approved; callers cannot raise them.
  • The broker runs a root-owned installed scanner asset whose version and digest are in policy and the authorization. It scans the same immutable spool bytes later transported, then rehashes immediately before constructing HTTPS JSON. Repository plugin-cache scanners are compatibility inputs, not trust roots.
  • Small requests stay in bounded memory. Spooling uses the fixed root state filesystem, no-follow exclusive creation, mode 0600, randomized names unrelated to repository input, immediate unlink-after-open where supported, per-run quotas, zero content logging, and cleanup/tombstone evidence on every terminal path.
  • For parity and simplicity, the provider secret is provisioned through the root admin client's controlling-terminal stdin into a fixed root-owned 0600 credential record. The daemon opens it with no-follow/owner/mode checks and never forwards it. This differs from the rejected same-UID authority-key file: repository workers are non-root and the provider key grants transport only, not authority signatures. Root compromise remains outside scope.
  • The HTTP client ignores proxy/base URL environment, sets the fixed origin/path itself, uses normal system TLS hostname verification, rejects every redirect, bounds headers/body/time, and records DNS/TLS/HTTP outcomes only as closed non-secret reason codes. Test endpoints require a compiled test mode, isolated authority namespace, loopback-only origin, and fixture-only credential class.

Consent and cadence

One FIDO-approved closed run may authorize automated provider dispatch only when its displayed scope includes provider openrouter, approved model/fallback set or model class, repository/candidate, lane set, policy digests, maximum calls/request bytes/response bytes/tokens/cost, and expiry. Each exact payload still receives a fresh single-use operation signature after broker scanning and budget reservation.

Payload changes within the already-approved classes and budgets require a new dispatch operation but not a new FIDO ceremony. Any destination, credential class, model set/class, routing/disclosure policy, repository, candidate/snapshot, lane set, authority generation, or limit expansion requires a new FIDO-approved run. Exact-digest interactive mode is narrower: the broker displays and confirms the exact combined digest inside the active run; the caller cannot supply the approval digest. Missing/expired authority never becomes trusted-boundary. It produces a signed host_authority_unavailable, host_disclosure_declined, or local_codex_fallback outcome.

Signed result and confidentiality model

The requesting client may receive bounded response bytes over the authenticated IPC session. Durable public receipts contain no content. They bind request digest, operation authorization digest, exact origin/path, requested/fallback models, actual response model, serving-provider provenance, provider generation ID, safe usage/token/cost fields, fallback status, response digest/bytes, terminal outcome, run/lane/candidate/substrate, prior-chain digest, and cleanup result. Missing or contradictory provider provenance is unverified or failure, never guessed.

Prompts/responses, bearer keys, headers, scanner excerpts, and secret-shaped diagnostics are excluded from logs, receipts, filenames, crash reports, and fixtures. The broker cannot turn a provider response into a passing repository-verification result; that requires the separate verification operation family.

Adversarial-review refinements

Wire identity must be signed before transport

The input manifest alone is insufficient because JSON construction can change semantics or bytes. The selected openrouter-chat-v1 mapping creates one messages entry per ordered UTF-8 part, preserving its system/user role and exact text without concatenation. Installed policy creates the mutually exclusive model or ordered models field, provider-routing object, stream: true, and stream_options.include_usage: true. The broker then canonicalizes the complete compact UTF-8 body, hashes it, and signs that final wire-body digest together with POST, /api/v1/chat/completions, fixed semantic headers, and the payload manifest before the first socket write. It rehashes the immutable body immediately before transport.

Credential storage is a root boundary, not a same-UID authority-key file

The provider key remains a root-owned transport credential. Provisioning is performed only by the Go admin binary reading echo-disabled /dev/tty; Python and plugin wrappers never see the key. Fixed 0700 parent directories and a regular 0600, root-owned, single-link, no-follow file are mandatory. Rotation uses an exclusive same-directory temporary file, file and directory fsync, atomic rename, generation update, daemon memory replacement, and zeroization. Core dumps are disabled and secret memory is locked where the platform permits. Backup exclusion is an operator requirement. Revocation zeroes daemon memory and unlinks the file; purge never claims reliable physical secure erasure on copy-on-write/SSD storage.

Response delivery is connection-bound

The daemon delivers response bytes once on the original authenticated socket and never exposes lookup-by-request-ID. The fixed automated client sends only the public signed result on stdout and writes response content to inherited anonymous pipe/socket descriptor 3 after verifying its file type; it accepts no response pathname. A disconnect or cancellation discards remaining content and zeroes buffers best-effort. Direct interactive mode may render to its existing controlling terminal, but never persists automatically. This prevents later broker retrieval; same-UID process-memory inspection remains part of the accepted compromised-session residual.

Replay state needs durable linearization

The root WAL records run/session/request IDs, nonce, sequence, request/body/authorization/prior digests, state, reserved attempt/network/cost budgets, timestamps, and terminal/cleanup digests. Reservation fsync consumes the sequence and scan-attempt quota. The final authorization/body digest is fsynced before send. Under the per-run lock, cancellation wins only if its terminal record fsyncs before the sending record; otherwise sending wins and cancellation aborts transport without refunding the send budget. Restart tombstones pre-send states as unsent and releases only network/cost reservations; a persisted sending state is indeterminate and remains consumed. No automatic retry or response retrieval is allowed.

Integration and migration findings

  • Replace the direct wrapper calls in Pipeline cascade, Pipeline OpenRouter exec, and the OpenRouter agent runner with the fixed broker client.
  • Strip/reject OPENROUTER_PAYLOAD_AUTHORIZATION, OPENROUTER_PAYLOAD_APPROVAL_SHA256, OPENROUTER_AUTHORIZATION_MODE, OPENROUTER_BASE, and OPENROUTER_API_KEY at automated child boundaries.
  • Preserve current ordered framing, scanner policy behavior, bundle resolution, model-slug validation, and return-code semantics as migration inputs; move authoritative execution into the broker.
  • Pipeline, dm-review, and Airlift consume signed broker results and record explicit Codex fallback. Workflow Kernel verifies the external-dispatch evidence family separately from inbound provider_attestation.
  • Direct interactive /openrouter retains a manual broker-owned exact-digest flow. A temporary explicitly named legacy direct mode may exist only for interactive migration, must never be selected automatically, and is not authoritative workflow evidence.

Residual risks and research gaps

  • Real libfido2, service-manager, provider, TLS, cancellation, and credential-rotation acceptance require later live gates on Linux and macOS.
  • OpenRouter may omit or vary serving-provider provenance. The broker must preserve raw safe fields as signed observations and label absent fields unavailable rather than infer them.
  • Host-wide same-UID egress denial cannot be promised without an OS isolation/firewall deployment. Candidate egress denial and authoritative-result integrity remain mandatory.
  • The existing schema/Python/Swift operation mismatch must be resolved with shared Go/Python golden vectors before any implementation builds on the partial files.
