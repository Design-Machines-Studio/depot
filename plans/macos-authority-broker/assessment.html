Assessment: shared run authority with separate verification and provider-dispatch families

Material scope change

The previous plan covered repository verification authority and Docker substrate evidence. PR15 demonstrates a separate P1: automated OpenRouter callers let the repository worker choose trusted-boundary or supply the digest it claims was approved. Ordered hashing proves byte identity, but not independent user or host authority.

Required direction: retain the Linux-first Go/libfido2 closed-run foundation, but add an independent external-provider operation family. The broker—not repository code—must scan the exact bytes, decide whether the closed run permits disclosure, hold the provider credential, perform the pinned HTTPS request, and sign the observed result provenance.

Gate reset: the old manifest, eight prompts, and OpenRouter adversary pack cover the verification-only plan and are superseded. This revision authorizes planning edits only.

Key requirements

  1. Preserve the approved cross-platform foundation: one Go core, pinned libfido2, one internal-UV FIDO approval per closed run, an in-memory ephemeral run signer, fixed root-owned service/socket paths, and equivalent Linux/macOS behavior.
  2. Keep repository verification/substrate operations separate from outbound provider-dispatch operations while sharing repository, run, candidate, authority, replay, and expiry bindings.
  3. Select broker-owned provider transport. Repository workers never receive the provider key, reusable approval material, unrestricted broker transport, or authority private keys.
  4. Bind every dispatch to the ordered payload manifest and per-part bytes/digests, pinned OpenRouter origin, requested/fallback models, workload, routing/disclosure policy digests, byte/response limits, repository/run/base/candidate/snapshot/lane/authority/substrate, nonce, sequence, boot/session, expiry, and single use.
  5. Move the canonical disclosure scanner into a fixed trusted broker installation; rehash immediately before network contact; reject malformed, binary, secret-bearing, reordered, oversized, or policy-mismatched content without sending.
  6. Pin production destination and reject redirects, proxy/base URL overrides, production credentials at test endpoints, model/policy downgrade, and caller-selected authorization environment variables.
  7. Return bounded response content only to the requesting client and public signed receipts containing digests/provenance—not prompt, response, API key, or secret-shaped diagnostics.
  8. Define run consent and exact-digest manual mode without allowing callers to self-approve; missing broker authority returns a signed local-Codex fallback/coverage-gap outcome and never silently becomes automated trusted-boundary execution.
  9. Migrate OpenRouter, dm-review, Pipeline, Airlift, and Workflow Kernel integration points, including direct interactive /openrouter, with canonical/generated ownership separated.
  10. Add Linux/macOS parity and adversarial coverage for same-UID bypass, replay, destination/model/policy mutation, credential discovery, direct curl, malformed streams, cancellation, concurrency, provenance forgery, and cleanup.
  11. Keep candidate containers without network, broker, Docker, FIDO, credential, authority-state, or service-manager access. State honestly that a same-UID host worker may have ordinary network access but cannot use the broker credential or mint broker-signed authoritative results.
  12. Do not implement, generate replacement prompts, mutate PR15, install, enroll, access credentials, contact a provider, validate live services, stage, commit, push, open a PR, merge, tag, publish, or release without later authorization.

Threat boundary and consequence

  • In scope: malicious candidate code, prompt-injected repository workers, same-UID attempts to self-promote authorization, key/env/file/process discovery, wrapper bypass, request mutation, replay, forged receipts, and accidental secret disclosure.
  • Supported guarantee: only the root broker can use the production provider credential or sign an authoritative dispatch/result chain. Candidate containers have no egress. Host workers may possess unrelated network access, but their calls cannot become authoritative broker evidence.
  • Out of scope: a deliberately compromised root account, kernel, authenticator, provider, TLS trust store, or fully compromised developer desktop; deliberate host-wide traffic interception; and a developer intentionally using separate personal credentials. These residuals must never be reported as defended.
  • Hardware/service/provider unavailability is a fail-closed coverage gap, not passing evidence. Local Codex may continue only with an explicit signed fallback outcome.
